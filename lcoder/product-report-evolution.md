# LCoder（慢牛 Maniu）建议演进产品设计全景报告（To-Be 理想蓝图）

状态：全盘演进指导报告（2026-11-22 修订定稿），面向「让人人都能用 AI 开发出想要的软件，且可维护、可持续、稳定、好用、易用」的核心目标制定，已补齐运行时防呆护栏、真相源约定、Phase 3a/3b 拆分与存量仓边界。

## 1. 产品要做什么（新定义的产品使命与设计哲学）

### 1.1 一句话产品定义
**LCoder（慢牛 Maniu）是一台「以活蓝图（Living Spec + 可交互原型）为中枢、前台傻瓜化所见即所得、后台工业级契约自治」的 AI 软件工厂。**

### 1.2 四个核心产品原则
1. **前台说人话、看画面（对小白零工程门槛）**：
   用户全程只用「产品语言」和「视觉画面」做决定（*我想做什么、这个界面长什么样、这里加个字段、跑起来让我试一下*）。把「签契约、哈希校验、规格绑定、P1/P3/P4 检查」全部收进后台自动驾驶，绝不逼普通用户当项目经理和架构师。
2. **后台守铁律、保活档（非一次性玩具，真可维护）**：
   保留并强化 `@maniu/kernel` 的 `.spec` 契约与 `allowed_paths` 写门禁，但把 `.spec` 从「静态历史档案」升级为**「永远与最新代码 100% 同步的活蓝图（Living Spec）」**——改了原型自动同步需求正文，开发中做了小微调自动追记到现行需求与规则表。
3. **大小变更智能分流（小改 10 秒直达，大改稳扎稳打）**：
   承认软件开发是动态演进的。提供统一的「提变更 / 加功能」入口，由系统自动识别是 **S 级微调（表单加字段）**、**M 级功能扩充（改核心规则）** 还是 **L 级跨端/新模块（加入桌面版）**，自动匹配不同重量的流程。
4. **自动驾驶 + 红线吹哨（稳定与效率兼得）**：
   90% 无破坏性风险的常规任务由 AI 自动完成「起草契约 → 自签 → 编码 → 跑测试门禁」全链路；只有触碰不可逆操作（删数据、改外部生产环境、破坏性迁移）或连续自测失败时，才吹哨请用户拍板。

### 2.2 重构一：立项与需求阶段——「图文双生（Doc ⇄ Prototype 双向联动）」

解决普通用户“看长篇文字想象不出软件长什么样，等看到画面想改时需求已锁定”的断层：

1. **立项即出画面（原型前置到定稿之前）**：
   - 用户点「从想法开始」答完几道关键选择题后，**需求分析师（`maniu-intake`）与原型设计师（`maniu-prototype`）在后台自动接力**：产出第一版需求正文的同时，立刻生成可交互的 HTML 原型。
   - 用户打开需求详情，第一眼看到的就是**「左文右图（或顶部切换图文、一键弹出独立交互预览窗）」**。
2. **点选原型修改 = 受控回写需求文档（以需求正文为唯一真相源）**：
   - **唯一真相源（SSOT）约定**：`.spec/requirements/REQ-xx.md` 始终是唯一契约真相源，HTML 原型是它的可视化投影，禁止 AI 静默覆写用户精修的业务规则。
   - 用户在独立原型预览窗口里 Alt+点击或开启选择模式选中某个表单/按钮，输入*“这里加一个必填的发票号输入框”*后，系统区分两类改动：
     - **纯视觉/布局微调**（圆角、间距、配色、排版）：仅执行 `prototype_patch` 更新原型，不污染需求正文；
     - **字段/交互/业务规则变更**（增删字段、改流程、改校验）：执行 `prototype_patch` 的同时，生成针对 `REQ-xx.md` 对应章节的受控补丁摘要，在界面展示可折叠的同步 Diff 与「撤销正文同步」入口，兼顾图文一致与规则安全。
3. **评审聚焦「图文一致性与高优风险」**：
   - 项目经理（`maniu-pm`）同时审阅需求正文与 HTML 原型，重点抓「原型里有按钮但没定义规则」「核心业务闭环缺漏」等高优问题；
   - 用户在紧凑表格里勾选采纳/拒绝/提问，确认无误后点「确认定稿」，**需求正文与原型图同时锁定为开发基线**。

### 2.3 重构二：全周期变更引擎——「S / M / L 三级智能分流 + 活文档同步」

解决开发中途或上线后**「给表单加个字段」vs「加入桌面版」**体量悬殊、入口怎么给、怎么判大小、改不改文档的核心难题：

#### 1) 用户看到什么入口？
在需求页顶栏、已确认需求详情页、任务页以及原型预览窗，提供统一的 **`[✨ 提变更 / 加功能]`** 按钮。用户不用纠结该去哪建任务还是建需求，只管用一句话说清诉求（例如：*“报销表单加个发票号字段”* 或 *“我想加入 Windows 桌面版”*）。

#### 2) 系统如何自动判断大小？（四维客观标尺）
提交后，变更分流器读取当前 `.spec`（已有需求状态、已有 Tracks、在途任务、涉及文件面），按 **4 个客观维度** 在 2 秒内给出分级建议卡：
1. **技术轨维度（Track）**：是否引入了 `project.yaml` 中尚未启用的新端/新轨（如新增 `desktop` 桌面端、新增外部数据库/第三方支付）？→ **是则直接判 L 级**。
2. **验收契约维度**：是否推翻或改变了已确认需求的核心计费、权限模型或主状态机？→ **是则至少判 M 级**。
3. **影响范围维度**：是否仅在既有页面/表单内增删非破坏性字段、调整交互细节、预计触及 ≤ 3 个文件且 `irreversible` 为空？→ **是则判 S 级**。
4. **生命周期维度**：目标需求当前还在 `draft`（直接走草稿修改），还是已在 `confirmed / released`（走 S/M/L 演进通道）？

#### 3) S / M / L 三级通道分别怎么走、哪些文档会改？

| 变更级别 | 典型例子 | 流程怎么走（最快路径） | 哪些文档自动改、哪些不动 |
| --- | --- | --- | --- |
| **🟢 S 级：局部微调 / 补漏**<br>*(Quick Patch)* | • **开发中发现某个表单要加个字段**<br>• 改按钮位置、文案、列表排序、非核心校验<br>• 修具体小 Bug | **【免重审 · 10 秒直达代码】**<br>用户点一次「确认按小改执行」：<br>1. 若对应表单的开发任务还在进行中，直接把字段要求追加进该任务契约与会话；<br>2. 若原任务已收口，后台自动创建一条关联原需求的 **C 级快修任务** 并自动派给开发人才改代码、跑单包快车道门禁。 | • **需求文档（`REQ-01.md`）**：**自动轻量同步！** 通过内核新增的 `requirement_amend` 工具，在不改变 `confirmed` 状态、不新建 `REQ-02`、**不重跑评审**的前提下，直接更新 `REQ-01.md` 对应表单段落，并在末尾变更记录追加一行 `[S级微调] 报销表单新增发票号字段`。<br>• **原型图**：按需可选局部 `prototype_patch`，不强制重生成。<br>• **历史评审报告**：封存不动。 |
| **🟡 M 级：功能扩充 / 规则变更**<br>*(Feature Delta)* | • 给账本增加「月度预算超支提醒与图表」<br>• 修改已确认的退款冲减统计口径 | **【增量评审 · 只评差异 · 拆增量任务】**<br>1. 在原需求 `REQ-01` 上开启一次**增量修订（Delta）**，生成只包含变更章节的对比提案与局部原型更新；<br>2. 只对增量部分做一次快速风险评审，用户点确认后 `REQ-01` 升版为 `v2（已确认）`；<br>3. 研发经理只针对 `v1 → v2` 的增量拆出 1–2 个 B 级开发任务。 | • **需求文档**：`REQ-01` 升级为 `v2` 快照，保留 `v1` 历史快照可对比。<br>• **原型图**：更新对应功能区块。<br>• **任务与契约**：已完成的老任务不动，只新增 1–2 条增量任务与契约。 |
| **🔴 L 级：新端 / 新大模块 / 架构演进**<br>*(Major Milestone)* | • **「开发到一半，我想加入桌面版」**<br>• 「接入多账号团队协作与云端同步」 | **【独立里程碑需求 · 架构师先行 · 开启新轨】**<br>1. 系统明确提示：*“加入桌面版属于跨端重大扩展，将作为独立需求 `REQ-02` 立项，不打断当前正在进行的开发。”*<br>2. 自动唤醒 **架构师（`maniu-architect`）** 先在 `project.yaml` 开启 `desktop` 技术轨，评估如何复用现有后端/业务逻辑、规划桌面壳目录与打包边界；<br>3. 独立走完 `REQ-02` 的原型生成 → 评审定稿 → 拆出带 `track: desktop` 的任务系列排入看板。 | • **项目配置**：`project.yaml` 正式登记新增的 `desktop` 轨。<br>• **需求与原型**：生成全新的 `REQ-02` 需求文档与桌面端专属原型，与 `REQ-01` 解耦。<br>• **规格与任务**：新增 `desktop` 轨专属规格条目与任务群。 |

#### 4) 防呆护栏：运行时自动升级（Escalation）与累计漂移治理
- **运行时自动升级**：分类弹窗的 S 级判定只是准入预判；一旦在起草契约或写代码阶段触发任意红线（需改文件突破原定范围、`irreversible` 不可逆项非空、涉及持久化 schema/权限模型变动、或自测连续失败），内核自动熔断 S 级快修并提示升级为 **M 级增量评审**，防止借小改通道偷渡大改。
- **累计补丁漂移治理**：内核对同一 `confirmed` 需求的 `requirement_amend` 记录补丁计数；累计达到阈值（默认 5 次）或在发布封存前，自动触发一次轻量一致性核对，把零散补丁与正文规则做交叉检查，避免“补丁叠罗汉”导致前后矛盾。

### 2.4 重构三：开发实施阶段——「幕后契约自治（Auto-Pilot） + 红线吹哨」

解决普通用户到了「任务」页看不懂 `drafting / contracted / implementing / verifying`、不知道怎么签契约和认领会话的问题：

1. **前台任务看板从 6 列简化为 4 列「结果语言」（并区分默认视图与 Pro 工程视图）**：
   - **`待开工（Queued）`**：已拆出、等待调度的任务；
   - **`AI 开发中（Building）`**：AI 正在后台自动起草契约、写代码、跑自测（卡片上用一句话实时显示进度，如 *“正在编写报销表单组件 (2/3)…”*）；
   - **`等你验收（Ready to Try）`**：代码与自动化测试已全绿，等待用户试玩点头；
   - **`已完成（Done）`**：用户验收通过并收口。
   - *(注：默认面向产品思维用户展示 4 列结果视图；内核底层的 `drafting / contracted / implementing / verifying` 6 列状态机、契约哈希校验与 P1/P3/P4 明细 100% 保留，收纳在任务详情的「工程治理明细」与显式 Pro 视图开关中，避免界面在小白与极客之间摇摆。)*
2. **默认开启安全任务的「契约自动签署与自动流转」**：
   - 需求定稿拆出任务后，用户只需点一次 **`[🚀 开始自动开发]`**；
   - 内核利用已有的 AI 自签三重闸门（`automation.yaml` 开启 `sign: auto` + 任务 `irreversible` 不可逆列表为空 + 自动契约复核通过），在后台**自动完成契约起草、签署、会话绑定、编码与快车道门禁测试**，一路自动推到「等你验收」。
3. **高危红线吹哨 + 失败熔断 + 任务级安全点（Checkpoint）**：
   - **不可逆红线吹哨**：只有当某条任务涉及**不可逆风险**（如删改已有持久化数据字段、执行外部环境变更、需要用户提供第三方密钥）时，任务卡才暂停并在右下角提示用户：**「⚠️ 需你确认：任务 T-05 将修改本地数据库表结构，是否授权执行？」**。
   - **重试与成本熔断**：单任务自测连续失败达到上限（默认 3 次）强制暂停吹哨，避免死循环空耗 Token；弹窗用人话给出失败原因和三个明确选项：`换思路重试` / `回滚到任务前状态` / `人工介入`。
   - **任务级安全点（一键撤回）**：每次 S 级快修或任务自动开工前，内核记录本地安全基线（只使用本地安全提交/快照，严守不 `git push`、不强覆盖远端红线）；用户验收不满意时，除了“打回重修”，还能一键**「撤销本次改动」**，把心理安全网拉满。

### 2.5 重构四：测试与验收阶段——「一键实窗试玩 + 验收清单打勾 / 指哪打回」

解决普通用户看不懂 `.log` 测试证据、不知道做出来的软件到底好不好用的问题：

1. **按项目形态分层的一键试玩托管（`[▶ 启动试玩]`）**：
   - 当任务进入「等你验收」列，卡片与详情页主按钮直接显示 **`[▶ 启动试玩 / 查看真实效果]`**；
   - **UI 类项目（Web / Desktop）**：桌面宿主读取 `.spec/env.yaml` 中的开发启动命令，托管子进程全生命周期——自动检测并避让端口冲突、关闭试玩窗或退出应用时彻底回收子进程树防止僵尸进程；若遇依赖缺失或启动报错，直接把可读错误摘要喂回开发会话一键修复；
   - **非 UI 类项目（API / CLI / SDK / 库）**：自动切换为「交互式试跑与样例输入/输出验证卡片」，避免假设所有软件都有可视化窗口。
2. **人话验收清单（Checklist）**：
   - 详情页把该任务对应的验收标准列成 3–5 条直白清单：
     - `✅ 自动测试已通过（类型检查 + 12 项单元用例全绿）`
     - `☐ 请你试玩确认：新增一笔带发票号的报销后，月度汇总金额实时刷新`
3. **双向出口：`[✅ 验收通过]` vs `[🔧 这里有问题，打回重修]`**：
   - **验收通过**：用户点通过 → 后台自动调用 `task_close` 完成 P1/P3/P4 收口。
   - **打回重修**：用户试玩发现毛病（比如*“点保存按钮没反应”*或*“发票号输入框太窄”*），直接点 **`[🔧 这里有问题，继续改]`** 输入一句话现象 → 内核自动将该任务从 `verifying` 退回 `implementing`，原开发会话带着用户的反馈和运行日志立刻返工修复，修好重跑测试后再请用户试玩。

### 2.6 重构五：版本上线与持续迭代——「活蓝图封存（Living Spec Release）」

1. **一键发布里程碑版本**：
   - 当某条需求下的所有任务均「验收通过」，系统提示 **`[🎉 全部功能已就绪，确认发布本版本]`**。
   - 点击后，内核自动核对所有 S 级补丁均已合入需求现行本与 `rules.yaml`，将需求置为 `released`，并生成本地干净的 Git 提交与版本标签（如 `v1.0`）。
2. **永不腐烂的下一代起点**：
   - 因为每一次 S 级小改、M 级扩充和打回重修都实时维护了 `.spec` 里的需求现行本、HTML 原型和规格规则，**仓库里的 `.spec` 永远是此时此刻软件 100% 真实的说明书**。
   - 半年后用户想做 V2.0 或加桌面版时，任何新启动的 AI 人才读入 `.spec`，都能瞬间掌握全盘现状，彻底告别传统 AI 编程“越改越乱、最后只能删库重来”的宿命。

### 2.7 存量老仓库接管边界（Brownfield Onboarding Policy）

本演进蓝图 v1 优先保障**「从 0 到 1 新建项目（Greenfield）」**与**「已具备 `.spec` 的持续演进项目」**；对尚无 `.spec` 的已有代码老仓库，明确轻量接管边界，避免把老项目强行塞进重型立项流：

1. **轻量建档而不强求补齐历史原型**：首次打开已有代码仓库且无 `.spec/` 时，提供「接管现有项目」入口——AI 扫描目录结构、包清单与现有文档，生成轻量 `project.yaml` 与基线 `REQ-00（现状基线说明）`，不强制为存量页面补画 HTML 原型。
2. **直接接入 S / M / L 变更引擎**：基线建档完成后，用户即可直接通过 `[✨ 提变更 / 加功能]` 对老项目发起 S 级小修、M 级功能扩充或 L 级新模块扩展，在持续迭代中逐步沉淀活蓝图。
