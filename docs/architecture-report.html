开篇 1

为什么要用它#

一句话结论AI 写代码很快，但「为什么改、改到哪、算不算完」这三件事，光靠聊天记录留不住；LCoder 把它们变成仓库里能查的文件和能拦住人的步骤。

先说四个痛点

  1. 说不清在干什么。需求、当时的决定、验收口径散在几百条聊天里。过几天再问「这条为什么这么改」，只能靠回忆，拼不回来。产品文档把这叫「不知道什么算完成」。
  2. 多件事并行会互相踩。两个人或多个窗口同时改一个仓库，改一处坏一处；谁负责哪块、哪些文件能碰，没有写在代码里的边界。
  3. 看起来做完了，其实没验。测试跑绿只说明代码能编译、已有用例没红，不说明新功能真的对；界面没点过就报完成，是 agent 开发里最常见的假完成。
  4. 长会话会把前面的约定忘掉。今天（2026-11-07）在本机实测：模型名义上支持百万字上下文，大约到十一万字就开始自动摘要；摘要后只剩六千字左右，前面说过的禁令、口径和取舍跟着丢了。

再说三个让人想用的地方

  • 一个工作台看全。任务板、规格规则、契约、验收证据和对话在同一个窗口里，不用在几个工具之间来回切。
  • 每件事都有状态，AI 不能自己越级。任务从起草到关闭是固定几步；没签契约就看不到改代码的工具，模型想跳步也没有入口。
  • 干完要交作业。证据存进仓库，契约和签名留在文件里，会话过程有日志；事后能回看，而不是只留下一句「已完成」。

依据：产品定位与「不知道什么算完成」见 docs/prd-and-design.md:13；并行边界与工作目录硬闸见 packages/lcoder/workspace/src/client/scheduling.ts:159；固定步骤与工具收放见 packages/lcoder/kernel/src/kernel/task-store.ts:21、packages/lcoder/kernel/src/kernel/surface.ts:29；证据只认非空文件见 packages/lcoder/kernel/src/kernel/evidence-store.ts:26；「模型看得见就必须留档」见 docs/architecture.md:128。第 4 条是本机实测记录，不是仓库源码结论；压缩机制见 6.5。

开篇 2

它怎么解决#

一句话结论它不靠模型自觉，而是把「先签字、再动手、留证据、危险动作归人」做成代码里的步骤。

第一步：先立字据再动工

接到一件事，先写一张「字据」：要做什么、不做什么、怎么算过、允许改哪些文件。没签字之前，模型能读代码、查规则、起草字据，但看不到改文件的工具；签完字、人确认推进，才会出现改代码和跑命令的权限。

第二步：干完要交作业

收工不是嘴上说完成。收口前会逐条检查：涉及的规则有没有对应到真实代码位置、涉及不可逆项时该签的字是不是还覆盖当前正文、要求留下的证据是不是都有且非空。三样全过，任务才允许进入「已关闭」。

第三步：危险动作只有人能做

签合同、推进任务状态、批准方案、合并分支、推送远端、部署上线，这些都不在模型能调用的工具清单里。模型可以把准备工作做到位，最后那一下必须由人点。

两层保障：不靠自觉，靠拦

工具按阶段收放。每个任务阶段只放行一份工具清单，不在清单里的工具等于不存在；配置漏了是「用不了」，不是「可以越权」。

允许改的路径是代码拦的。任务写了允许范围，改范围外的文件会被直接拒绝，并告诉你该改任务范围或换任务——这不是提示词，是代码里的闸。

依据：起草态工具面见 packages/lcoder/kernel/src/kernel/surface.ts:29；失败默认关闭见 packages/lcoder/kernel/src/kernel/surface.ts:107；允许路径硬闸见 packages/lcoder/kernel/src/tools/edit-tools.ts:136；收口三检查见 packages/lcoder/kernel/src/tools/task-tools.ts:201；签署与推进只走人机命令见 packages/lcoder/kernel/src/commands/contract-sign.ts:4、packages/lcoder/kernel/src/commands/task-contract.ts:6；没有 push 见 docs/PROJECT-RULES.md:23；部署只跑 human 命令见 packages/lcoder/kernel/src/commands/deploy.ts:1。

开篇 3

理想状态#

一句话结论目标是让一个仓库里的每一次改动都能回答四个问题：属于哪个任务、签了什么、证据在哪、谁验收。

先把话说清：这一章写的是目标，不是现状。下面三层是产品想达到的样子；当前做到哪一步、哪些还没做，每层末尾都如实标注，完整清单在第 12 章。

对个人：一件事从头到尾查得到

目标状态是：回头查任何一处改动，都能顺着任务找到当时的契约、签名、验收证据和会话记录，不用再翻聊天。今天已经做到的是任务、契约、签名、方案与证据都以文件形式留在仓库里，界面能把它们读出来（packages/lcoder/workspace/src/client/projection.ts:415）；会话日志也按「模型看得见就必须留档」保存（docs/architecture.md:128）。还没做到的是「每一次改动自动挂到任务上」的独立入口——目前主要靠任务、证据文件和会话日志三处对照回看。

对团队：多人多窗口并行，不互相踩

目标状态是：每个人或每个窗口有自己的隔离工作目录和固定端口，调度时工作目录不同就不复用、不入队，收口走同一套动作，谁也不会把改动写进别人的工作副本。今天已经做到的是调度层把「工作目录不同」当作硬闸，跨工作树不复用、不入队（packages/lcoder/workspace/src/client/scheduling.ts:159）；并行线一条工作树、一套端口的规矩写在项目规则里（docs/PROJECT-RULES.md:134）。还没做到的是工作树的创建、端口分配与收口清理仍靠脚本和人，产品里没有一键入口。

对新用户：装好就能开始

目标状态是：Windows 与 macOS 都能开箱启动，登录后有一份免费额度，可以先把「立项分析」跑通，再决定要不要继续。今天 Windows 开发链路可用；macOS 打包仍是 T-80 待办，真实云端也还没合入主线，桌面默认连的是本机 mock（docs/tasks.yaml:881、docs/active-context.md:18）。所以「装好即用」目前只是 Windows 开发机上的部分事实，不是双平台现状。

诚实的达成度：单机、单仓库、按任务走的主链路已经能跑；多人协作、双平台开箱、真实云端与免费额度仍在建设中。技术实现见第 3–10 章，未实现与未验逐条列在第 12 章。

开篇 4

做不到的部分与应对#

一句话结论它能把「乱」和「忘」管住，但管不住「错」；下面五件事必须靠人或靠流程兜底。

做不到的事为什么做不到现在怎么缓解
模型会编，代码不保证对语言模型给的是概率上合理的输出，不是正确性证明；它可能自信地写错，也可能漏掉边界。门禁加人签加证据三道兜底：检查落点、签名和证据是否齐全，关键动作由人签。但这只能提高发现概率，不能根治。
上下文有限，长会话会忘今天在本机实测：名义百万字，约十一万字开始自动摘要，摘要后只剩六千字左右，前面的禁令和口径会丢。代码里的压缩阈值也按上下文容量的比例算（0.8 / 0.16），不是固定字数。操作约定：拆窄工单，一次只做一件事；长输出落文件、只读尾部；压缩发生多次就换新会话，把关键约定重新写进任务或契约。
真实环境验不了真实云端、真实短信与支付（支付首期未做）、签名证书、macOS 真机都不在这台开发机上；工具跑不出这些结论。只能由人验；工具如实记「未验」，不把计划写成现状。清单见第 12.2 节。
本机环境差异这台机器向操作系统询问「文档」目录会挂死，导致「打开仓库」永远没回应。这是特定机器的坑，不是产品能力。用配置项把文档目录指到本检出的真实目录绕开（lcoder/desktop-profile.patch.yml:19）；换机器要按 docs/PROJECT-RULES.md:127 重配。
需求本身对不对机器只能把给定的东西做快；方向错了，它会把错的东西更快地做出来。先用立项分析把现状和目标问清，关键取舍由人拍板：方案批准、契约签署都不在模型工具里。

依据：三道检查见 packages/lcoder/kernel/src/checkers/index.ts:46、packages/lcoder/kernel/src/checkers/index.ts:97、packages/lcoder/kernel/src/checkers/index.ts:162；压缩阈值见 lcoder/desktop-profile.patch.yml:95；长文件分段读取见 packages/lcoder/kernel/src/tools/edit-tools.ts:165；真实环境未验见 docs/desktop-release.md:313；方案批准与契约签署只走人机命令见 packages/lcoder/kernel/src/commands/proposal-approve.ts:4、packages/lcoder/kernel/src/commands/contract-sign.ts:4。第 2 条的数字是本机实测记录，不是仓库源码结论。

1.1everything-is-a-plugin 与 Cordis#
